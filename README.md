# Sistema Centinela (SICEN)

Aplicación para la **Prefectura del Puerto de Montevideo**: API **Node.js (Express, ESM)** con **MongoDB (Mongoose)** y autenticación **JWT**, más SPA **React 18 + Vite 5** y **React Router 6**. Estilos: **Bootstrap 5.3** (CDN) e iconos Bootstrap Icons; tema claro/oscuro con `data-bs-theme` y estilos en `SICEN-front/src/styles/sistema.css`, `SICEN-front/src/styles/menu-tiles.css` (tarjetas de menú e inicio) y `SICEN-front/src/styles/user-state-badges.css` (barras de especializaciones en el inicio).

## Estructura del monorepo

| Ruta | Rol |
|------|-----|
| **`SICEN-back/`** | Servidor Express. Sirve la API bajo **`/api/*`** y, si existe el build, la SPA desde **`SICEN-back/public/`**. |
| **`SICEN-front/`** | Código fuente React. **`npm run build`** genera estáticos en **`../SICEN-back/public`**. |
| **Raíz** | `package.json` con **Prettier** para formatear todo el repo (`npm run format`). Aquí se instala solo Prettier; no sustituye los `node_modules` de front ni back. |

Documentación de paleta y tokens CSS: **`SICEN-front/PALETA_COLORES.md`**.

### Alcance del producto

SICEN es una **plataforma operativa amplia** para la Prefectura: bases de datos (buques, gente de mar), gestión de unidades, usuarios, herramientas externas y, de forma **no central** en la experiencia diaria del usuario, **multas** (vehículos terrestres, buques y personas). El menú principal y la tarjeta de datos personales **no priorizan** el módulo de multas; las pantallas y API relacionadas con multas **siguen disponibles** y se irán **reforzando y alineando** en próximas entregas.

| **Colección `vesselInspections`** | Modelo Mongoose (`SICEN-back/src/DAO/models/mongoose/vesselInspections.mongoose.js`) con `vesselId` (ref `vessels`), `arrivalDate`, **`inspectionDate`** (día de la diligencia, puede diferir del ingreso), `arrivalPort` (mayúsculas), `cialaPriority` (texto libre normalizable a 1 o 2), `inspectionPerformed`, **`inspectionPDF`** (URL pública del reporte), `deficiencies: [{ code, name, rule, actionsTaken: [Number], ISMrelated }]`, **`inspectors: [String]`** (emails en minúsculas de quienes firmaron la diligencia) y `metadata: { createdBy, lastModifiedBy }` (auditoría por email). ## Desarrollo

### Una sola URL (API + SPA compilada)

1. Completá **`SICEN-back/.env.development`** (al menos MongoDB y, en serio, un `JWT_SECRET` propio aun en local).
2. Desde **`SICEN-back`**:

   ```bash
   npm run dev
   ```

   El script **`predev`** ejecuta el **build del cliente** y luego **nodemon** sobre `src/app.js`. Abrí **`http://localhost:<PORT>`** (p. ej. 3000): mismo origen para la SPA y **`/api/*`**.

### Front con recarga rápida (Vite)

En otra terminal, desde **`SICEN-front`**:

```bash
npm run dev
```

Abrí **`http://localhost:5173`**. El proxy de Vite reenvía **`/api`** a **`http://localhost:3000`**; el backend debe estar corriendo por separado (p. ej. `cd SICEN-back && npm run dev` **sin** depender del build previo del front, o con un build ya hecho según cómo prefieras trabajar).

### Cliente y JWT

El front guarda el access token en **`localStorage`** bajo la clave **`sicen_auth_token`** y envía **`Authorization: Bearer <token>`** en las peticiones a la API (`SICEN-front/src/api/client.js`). Login y signup guardan el token; logout y errores de sesión lo limpian cuando corresponde. Tras completar el manual, `completeUserTutorial()` actualiza el usuario en sesión vía `AuthContext.refresh()`.

## Producción / despliegue

Necesitás el repo con **`SICEN-front`** y **`SICEN-back`**, **`SICEN-back/.env.production`** con **`JWT_SECRET`** y el resto de secretos, y la carpeta **`SICEN-back/public/`** generada antes del arranque.

```bash
cd SICEN-back
npm install
cd ../SICEN-front && npm install && npm run build
cd ../SICEN-back
npm start
```

Equivalente: desde **`SICEN-back`**, `npm run build` (compila el cliente) y luego **`npm start`**.

El hosting debe servir el proceso Node que ya expone estáticos y la API, o adaptar proxy estático según tu plataforma.

## Emails (recuperación y cuentas)

Los enlaces de correo usan la URL pública derivada de **`PUBLIC_APP_URL`** o **`API_URL`**. La recuperación apunta a la ruta React de restablecimiento (p. ej. **`/restablecer?token=...&email=...`**). La API valida tokens según los endpoints documentados en el código de **`tokens`**. Las solicitudes de cuenta (`POST /api/users/newAccount`) envían correo interno con tipo de cuenta, datos del solicitante, justificación y un botón/enlace a **`/usuarios/nuevo?prefill=…`** para que un admin cree la cuenta con los datos precargados.

## Seguridad (resumen)

| Área | Política |
|------|----------|
| **Auth (JWT)** | `GET /api/sessions/me`: sin `Authorization` → usuario nulo; token inválido → `401`. Rutas protegidas: **`Authorization: Bearer`**. `POST /logout` es informativo (JWT stateless; el cliente borra el token). |
| **Tutorial obligatorio** | Tras login, si `userTutorial !== true`, la API de módulos operativos responde **`403`** con código **`USER_TUTORIAL_REQUIRED`** (mensaje orienta a completar Manual usuario). Orden de middlewares en rutas protegidas: autenticación → rol (si aplica) → **`checkUserTutorial`**. |
| **Tokens de recuperación** | Endpoints públicos; conviene **rate limiting** en producción. |
| **Usuarios** | Operaciones sensibles requieren roles (**admin** / **superAdmin** / reglas por ruta). Roles de producto adicionales (`skipper`, `seaman`, `agency`) no otorgan por sí solos privilegios de panel. Datos de contraseña no se exponen en respuestas de perfil. |
| **Multas** | API y pantallas de multas (vehículos, buques, personales) disponibles; permisos según rol (**admin**, **contable**, etc.). Las **pruebas** (`.jpg` ≤ 5 MB, hasta 3 por multa) viven **fuera de `SICEN-back/public/`** en `SICEN-back/storage/<tipo>FineProves/` y se sirven solo bajo el prefijo público correspondiente (`/uploads/carFineProves/`, `/uploads/shipFineProves/`, `/uploads/personalFineProves/`); los nombres siguen el patrón **`<fine_number><N>.jpg`** y al eliminar/editar se limpian del disco. La **home** ya no muestra contador ni acceso rápido personales a «mis multas» (el foco de producto es más amplio). |
| **Procedimientos en disco** | Solo **admin** / **superAdmin** pueden subir o eliminar archivos en las carpetas de procedimientos por división; el resto de roles solo consulta y descarga. |
| **Buques (baja)** | El `DELETE` en `/api/vessels/by-business-id/:vesselId` exige **admin** o **superAdmin**. En la SPA, `/base-buques/eliminar` usa `ProtectedRoute admin` y el menú de buques solo muestra la tarjeta **BORRAR BUQUE** a esos roles. |

Pendientes habituales en producción: **rate limiting** (login, recuperación, altas de cuenta), endurecer CORS, y desactivar **`POST /signup`** si no querés registro público.

## Convenciones internas (Cursor skills y rules)

Para mantener consistencia entre módulos, el repo guarda guías reutilizables en **`.cursor/`** que el agente (y cualquier colaborador) debe consultar antes de implementar patrones similares.

### Rules (`.cursor/rules/`)

| Archivo | Alcance |
|---------|---------|
| `proactive-skill-creation.mdc` | Obliga a crear o actualizar un skill en `.cursor/skills/<nombre>/SKILL.md` cuando una implementación introduce un helper compartido, refactoriza varias pantallas a una estructura común, fija una convención de UI o define un contrato backend reutilizable. Antes de crear uno nuevo, revisar si encaja en un skill existente. |
| `user-facing-copy.mdc` | Todo texto visible en SICEN-front (labels, `form-text`, placeholders, mensajes de error, alertas, popovers/hints, legendas de menús) debe estar en español rioplatense centrado en lo que el usuario tiene que hacer. **Prohibido** exponer rutas del sistema (`/uploads/...`, `SICEN-back/storage/...`), nombres de campos del esquema (`vesselId`, `metadata.createdBy`), identificadores internos o herramientas técnicas (Multer, Mongoose, multipart). Los detalles técnicos van en JSDoc / comentarios / skills, nunca en el JSX. |

### Skills (`.cursor/skills/<nombre>/SKILL.md`)

| Skill | Cubre |
|-------|-------|
| `delete-flow-pattern` | Confirmación y feedback de eliminaciones vía `confirmDelete`, `notifyDeleteSuccess` y `notifyDeleteError` (`SICEN-front/src/utils/confirmDelete.js`). Reglas de copy, layout de botones, manejo de errores `{ ok, msg }` y listado de páginas que ya siguen el patrón (incluye `DeleteInspectionPage`). |
| `iframe-modal-pattern` | Embebido de sitios externos con el componente `IframeModal` (loading, cierre por `Escape`, soporte de logo invertido en dark mode). Documenta el fallback de enlace en nueva pestaña cuando el sitio rechaza el iframe (caso CIALA). |
| `inspection-active-year` | Ejercicio anual persistente en `localStorage` para Inspecciones más el resto del módulo: API de `inspectionExercise.js`, normalización de prioridades CIALA, convención **"Ingreso vs Inspección"**, dos pasos del flujo (registrar ingreso → completar diligencia), atribución de stats `byInspector` por el array `inspectors` (sin fallback a `createdBy`), filtros del endpoint paginado (`mine`, `inspectorEmail`, `inspectionDate`, `includePlaceholders`) y manejo de fechas en **UTC midnight**. |
| `backend-crud-module` | Patrón estándar para nuevos módulos CRUD del backend (Mongoose model → service → controller → router → cliente API). Convenciones: respuestas `{ ok, msg, ... }`, errores vía `httpError`/`handleError`, `metadata.createdBy/lastModifiedBy`, paginación con `mongoose-paginate-v2`, guards (`guarded` / `adminGuarded`). Ejemplo vivo: `vesselInspections`. |
| `paginated-search-table-pattern` | Pantalla con input de búsqueda + tabla paginada del backend + estado `loading` / `error`. | `notifications-pattern` | Inbox `notifications`, `notifyAudience`, campanita `NotificationsBell`, dedupe y fan-out por unidad/usuario. |
